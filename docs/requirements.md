# Требования к проекту My Cloud

Документ конкретизирует обязательные требования из исходного задания. Текст задания сохранён в `docs/assignment.md`.

## Роли

### Гость

Неаутентифицированный посетитель может:

- открыть главную страницу и прочитать информацию о приложении;
- перейти к регистрации и входу;
- зарегистрироваться с логином, полным именем, email и паролем;
- скачать файл по действующей публичной ссылке без раскрытия владельца, внутреннего пути и физического имени файла.

Гость не может просматривать списки пользователей и файлов или изменять данные хранилищ.

### Пользователь

Аутентифицированный обычный пользователь может:

- войти и выйти из приложения;
- просмотреть только собственное хранилище;
- загрузить файл с комментарием;
- скачать или открыть собственный файл;
- переименовать собственный файл;
- изменить комментарий к собственному файлу;
- удалить собственный файл;
- получить и скопировать обезличенную публичную ссылку на собственный файл.

Пользователь не может открывать административный интерфейс, просматривать список пользователей, менять роли, удалять пользователей или работать с чужим хранилищем.

### Администратор

Администратор обладает возможностями обычного пользователя и дополнительно может:

- открыть административный интерфейс;
- получить список пользователей без паролей;
- видеть логин, полное имя, email и признак администратора;
- видеть количество файлов и их суммарный размер для каждого пользователя;
- изменить признак администратора;
- удалить пользователя вместе с относящимися к нему файлами;
- перейти в хранилище любого пользователя, включая собственное;
- выполнять разрешённые файловые операции в выбранном хранилище.

Система не должна позволять случайно удалить или лишить прав последнего администратора.

## Валидация регистрации

### Логин

- содержит только латинские буквы и цифры;
- начинается с латинской буквы;
- имеет длину от 4 до 20 символов;
- уникален без неоднозначности регистра символов.

### Email

- соответствует формату адреса электронной почты;
- нормализуется перед сохранением;
- не раскрывается гостям и обычным пользователям.

### Пароль

- содержит не менее 6 символов;
- содержит хотя бы одну заглавную букву;
- содержит хотя бы одну цифру;
- содержит хотя бы один специальный символ;
- передаётся только по защищённому соединению в production;
- хранится только в виде стойкого хеша средствами Django;
- никогда не возвращается через API и не записывается в журнал.

Ошибки формы должны быть понятными, связанными с конкретными полями и позволять исправить данные без повторного заполнения корректных полей.

## Аутентификация и авторизация

- Состояние входа хранится в серверной сессии Django.
- Закрытые API требуют действительную сессию.
- Изменяющие запросы защищены CSRF-механизмом.
- Сервер проверяет роль и принадлежность ресурса при каждом запросе.
- Ограничения маршрутов React улучшают интерфейс, но не заменяют серверную проверку.
- Регистрация, вход и публичное скачивание являются открытыми операциями.
- Выход завершает текущую сессию.
- Ошибки возвращаются с корректным HTTP-статусом и в едином JSON-формате.

## Файловое хранилище

Для каждого файла сохраняются:

- владелец;
- оригинальное имя;
- уникальное физическое имя или относительный путь;
- размер в байтах;
- комментарий;
- дата и время загрузки;
- дата и время последнего скачивания либо `null`;
- криптографически стойкий публичный токен.

Правила хранения:

- базовый каталог задаётся настройкой окружения;
- в БД хранится только относительный путь внутри базового каталога;
- физическое имя не зависит от оригинального имени;
- одинаковые оригинальные имена разных пользователей не конфликтуют;
- пользовательский ввод не участвует в построении физического пути;
- при скачивании сервер указывает безопасно обработанное оригинальное имя;
- удаление записи и физического файла выполняется согласованно;
- внутренний путь и публичный токен не попадают в обычные API-ответы и журналы.

## Публичная ссылка

- Ссылка содержит только непредсказуемый токен.
- Ссылка не содержит логин, идентификатор пользователя, структуру хранилища, оригинальное или физическое имя файла.
- По действующему токену файл скачивается без сессии с оригинальным именем.
- Несуществующий токен не позволяет определить, существовал ли пользователь или похожий файл.
- Публичное скачивание обновляет дату последнего скачивания.

## Пользовательский интерфейс

- Приложение максимально реализует SPA-подход.
- Переменные данные загружаются асинхронно через REST API.
- Навигация зависит от сессии и роли.
- Поддерживаются прямое открытие маршрутов и страница 404.
- Для загрузки, пустых списков, успеха и ошибок предусмотрены явные состояния.
- Все кнопки действий имеют доступное имя и заметное состояние фокуса.
- Формы управляются React, имеют связанные подписи и доступные сообщения об ошибках.
- Интерфейс работает с клавиатуры и адаптируется к экранам шириной от 320 px.
- Анимация учитывает пользовательскую настройку `prefers-reduced-motion`.

## Сервер и конфигурация

- Backend реализуется на Python и Django.
- Основная СУБД — PostgreSQL.
- Настройки БД, секретов, хранилища, доменов и production-режима поступают из окружения.
- Миграции приводят чистую БД к актуальной схеме.
- После миграций идемпотентно создаётся начальный пользователь `admin`; пароль поступает из окружения или безопасного интерактивного ввода.
- Django обслуживает REST API и production-сборку React единым сервером приложения.
- Серверные события журналируются с датой, временем и уровнями `debug`, `info`, `warning`, `error` без утечки секретов.

## Технологические ограничения

- Используются последние стабильные совместимые версии пакетов на момент начала реализации.
- Frontend собирается Vite и управляется через Yarn Classic 1.22.22.
- Версия Yarn фиксируется через Corepack и поле `packageManager`.
- Файл `yarn.lock` обязателен; `package-lock.json` не используется.
- Используются React, Redux и React Router.
- Применяются только бесплатные зависимости с лицензиями, допустимыми для открытого проекта.
- Production-развёртывание выполняется на reg.ru.

## Критерии качества

- `yarn validate` последовательно выполняет линтер, frontend-тесты с покрытием и production-сборку.
- Frontend имеет 100% покрытия собственного тестируемого кода по statements, branches, functions и lines.
- Backend имеет не менее 80% общего покрытия; обязательные сценарии аутентификации, авторизации и файловых операций покрыты полностью.
- Django system check и все автоматические тесты проходят.
- CI повторяет воспроизводимую установку и проверки для Pull Request и основной ветки.
- Ручной smoke-тест покрывает регистрацию, вход, выход, файловые операции, публичное скачивание и административные действия.
- Проект разворачивается с нуля только по инструкции из итогового `README.md`.
