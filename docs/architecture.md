# Архитектура My Cloud

Документ описывает структуру проекта, модели данных, права доступа и устройство файлового хранилища. API и маршруты SPA будут описаны отдельно.

## Структура монорепозитория

```text
my-cloud/
├── backend/                 # Django, REST API, миграции и backend-тесты
│   ├── config/              # Настройки проекта и корневые URL
│   ├── users/               # Пользователи, сессии и административные операции
│   ├── storage/             # Метаданные и операции с файлами
│   └── manage.py
├── frontend/                # React, Redux, React Router и frontend-тесты
│   ├── src/
│   ├── package.json
│   └── yarn.lock
├── docs/                    # Требования и проектная документация
├── .env.example             # Пример переменных без секретных значений
├── .gitignore
├── PLAN.md
└── README.md
```

Frontend и backend разрабатываются раздельно, но публикуются как одно приложение. В production Django обслуживает API и собранную Vite версию SPA.

## Backend-приложения

### `users`

Отвечает за:

- пользовательскую модель;
- регистрацию;
- сессионные вход и выход;
- получение текущего пользователя;
- административный список пользователей;
- изменение прикладной роли;
- удаление пользователя.

### `storage`

Отвечает за:

- модель метаданных файла;
- загрузку и физическое размещение файлов;
- получение списка файлов;
- изменение имени и комментария;
- авторизованное и публичное скачивание;
- создание публичной ссылки;
- удаление файлов.

Операции с файловой системой выполняются в сервисном слое. Представления API не строят пути и не удаляют файлы напрямую.

## Модель пользователя

Рабочее имя модели: `users.User`. Модель наследуется от `AbstractUser`, чтобы использовать безопасное хеширование паролей, сессии и встроенные механизмы Django.

| Поле | Тип | Ограничения и назначение |
|---|---|---|
| `id` | `BigAutoField` | Первичный ключ, не используется в публичных ссылках |
| `username` | `CharField(20)` | Уникальный логин, 4–20 латинских букв или цифр, начинается с буквы |
| `full_name` | `CharField(255)` | Полное имя из формы регистрации |
| `email` | `EmailField(unique=True)` | Уникальный нормализованный адрес |
| `password` | поле Django | Хеш пароля; открытый пароль не сохраняется |
| `is_admin` | `BooleanField` | Прикладной администратор My Cloud, по умолчанию `False` |
| `storage_path` | `CharField(100)` | Уникальный относительный каталог вида `users/<uuid>` |
| `is_active` | поле Django | Позволяет штатно блокировать учётную запись |
| `is_staff` | поле Django | Технический доступ к Django Admin; не заменяет `is_admin` |
| `is_superuser` | поле Django | Технические права Django; не меняются через API My Cloud |
| `date_joined` | поле Django | Дата регистрации |

### Решения по пользовательской модели

- `AUTH_USER_MODEL` задаётся до первой миграции.
- Логин нормализуется в нижний регистр, поэтому `User1` и `user1` считаются одним логином.
- Email нормализуется в нижний регистр и проверяется на уникальность без учёта регистра.
- Прикладные проверки доступа используют `is_admin`, а не `is_staff` или `is_superuser`.
- Начальный пользователь `admin` получает `is_admin=True`; при необходимости работы с Django Admin ему отдельно назначаются технические флаги.
- Обычный API никогда не возвращает `password`, `storage_path`, `is_staff` и `is_superuser`.
- Запрещено удалять или лишать прикладной роли последнего активного пользователя с `is_admin=True`.
- `storage_path` создаётся сервером и не принимается из пользовательского ввода.

## Модель файла

Рабочее имя модели: `storage.StoredFile`.

| Поле | Тип | Ограничения и назначение |
|---|---|---|
| `id` | `BigAutoField` | Первичный ключ метаданных |
| `owner` | `ForeignKey(User)` | Владелец; индекс; удаление пользователя каскадно удаляет записи |
| `original_name` | `CharField(255)` | Имя, отображаемое и возвращаемое при скачивании |
| `storage_name` | `UUIDField` | Уникальное физическое имя, генерируется сервером |
| `relative_path` | `CharField(255)` | Уникальный относительный путь внутри базового каталога |
| `size` | `BigIntegerField` | Размер в байтах, значение неотрицательно |
| `comment` | `TextField` | Комментарий пользователя, может быть пустым |
| `uploaded_at` | `DateTimeField` | Дата и время загрузки, назначается при создании |
| `last_downloaded_at` | `DateTimeField` | Последнее успешное скачивание, изначально `null` |
| `public_token` | `CharField(43)` | Уникальный URL-safe токен из 32 случайных байт |

### Ограничения и индексы

- Индекс по `(owner, uploaded_at)` ускоряет выдачу файлов пользователя в порядке загрузки.
- `storage_name`, `relative_path` и `public_token` уникальны.
- `size` имеет ограничение `size >= 0`.
- `original_name` не может быть пустым после безопасной нормализации.
- Одинаковые `original_name` разрешены, поскольку физические имена всегда различаются.
- `owner`, `relative_path`, `storage_name` и `public_token` не изменяются операцией переименования.

## Физическое хранение файлов

Базовый каталог задаётся переменной `FILE_STORAGE_ROOT` и находится за пределами каталога со статическими файлами.

```text
FILE_STORAGE_ROOT/
└── users/
    └── <uuid-хранилища>/
        └── <uuid-файла>
```

Пример относительного пути:

```text
users/0c79cb20-8200-427b-ad73-c16d5674d09d/6bd684fe-8b87-4d58-99c6-f181cf546bc7
```

Правила:

- абсолютный путь вычисляется только серверной функцией из доверенного базового каталога и сохранённого относительного пути;
- после вычисления проверяется, что путь остаётся внутри `FILE_STORAGE_ROOT`;
- логин, оригинальное имя и комментарий никогда не участвуют в физическом пути;
- имя из HTTP-загрузки очищается от каталогов, управляющих символов и опасных последовательностей;
- файл не раздаётся веб-сервером напрямую как media-ресурс: права и дата скачивания обрабатываются Django;
- в production каталог должен сохраняться между перезапусками приложения и иметь минимально необходимые права ОС.

## Жизненный цикл загрузки

1. Сервер проверяет сессию, право на выбранное хранилище, наличие файла и лимит размера.
2. Оригинальное имя нормализуется для отображения и заголовка скачивания.
3. Генерируются `storage_name`, `relative_path` и `public_token`.
4. Поток записывается во временный файл внутри целевого файлового раздела.
5. После успешной записи и проверки размера временный файл атомарно перемещается в целевой путь.
6. В транзакции создаются метаданные.
7. При ошибке временный или перемещённый файл удаляется, чтобы не оставлять бесхозные данные.

Загрузка не считывается целиком в память. Используются порционные данные Django upload handler.

## Жизненный цикл скачивания

1. Для закрытого маршрута проверяются сессия и право на файл; для публичного — токен.
2. Проверяется наличие физического файла внутри разрешённого каталога.
3. Формируется потоковый ответ без загрузки всего файла в память.
4. Заголовок `Content-Disposition` получает безопасно закодированное оригинальное имя.
5. Только после начала успешной выдачи обновляется `last_downloaded_at`.
6. В журнал записывается идентификатор записи и вид скачивания без токена и полного пути.

## Переименование и комментарий

- Переименование меняет только `original_name`.
- Физический файл и `relative_path` не перемещаются.
- Новое имя проходит ту же нормализацию, что и имя при загрузке.
- Комментарий хранится как обычный текст и экранируется React при отображении.
- Для имени и комментария устанавливаются документированные лимиты длины запроса.

## Удаление файла и пользователя

Файловая система не поддерживает транзакции БД, поэтому операции организуются через сервисный слой:

- перед удалением проверяются права и расположение физического файла;
- запись удаляется в транзакции;
- физическое удаление выполняется через `transaction.on_commit`;
- отсутствие файла на диске не мешает очистить устаревшую запись, но фиксируется предупреждением;
- ошибка физического удаления фиксируется как `error` и оставляет диагностируемый бесхозный файл, а не восстанавливает уже подтверждённую пользователю запись;
- для поиска и очистки бесхозных файлов предусматривается служебная management-команда.

При удалении пользователя сначала собираются принадлежащие ему пути, затем в транзакции удаляется пользователь и каскадные записи, а после commit очищается его каталог.

## Публичный токен

- Создаётся через `secrets.token_urlsafe(32)` и содержит около 256 бит случайности.
- Уникальность дополнительно контролируется БД.
- Токен не содержит данных владельца или файла.
- В API владельцу возвращается готовый URL, но токен не попадает в списочные ответы и журналы.
- Неверный токен приводит к обычному `404 Not Found` без уточнения причины.

Отзыв и повторная генерация публичной ссылки полезны для безопасности, но относятся к дополнительным функциям и не должны задерживать обязательный MVP.

## Инварианты безопасности

- Решение о доступе всегда принимает backend.
- Идентификатор объекта не является разрешением на доступ.
- API не принимает абсолютные пути.
- Пользовательский ввод не используется как физическое имя.
- Пароли, session cookie, CSRF-токены, публичные токены и полные пути не журналируются.
- Ошибки закрытых ресурсов не раскрывают существование чужих файлов сверх необходимого.
- Изменение роли и удаление пользователя блокируются, если действие оставит систему без активного администратора.
